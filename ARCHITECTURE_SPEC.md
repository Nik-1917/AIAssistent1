# Архитектурная спецификация AI-ассистента для Android

## Цель

Создать нативное Android-приложение с текстовым AI-ассистентом. Архитектура должна позволять без переработки основного чата добавить голосовой ввод, доступ к календарю и агентные инструменты.

## Базовая конфигурация проекта

- Package name и application ID: `com.example.aiassistent1`.
- Минимальная версия Android: Android 11 (API 30), в соответствии с текущей конфигурацией проекта.
- Kotlin, Android Gradle Plugin и Compose BOM берутся из `gradle/libs.versions.toml`. Не понижать версии без отдельной задачи на совместимость.
- Не использовать Hilt, Dagger и reflection.
- Зависимости внедряются вручную через `AppModule`.
- Все новые комментарии в production-коде писать на русском языке и только там, где они объясняют нетривиальную причину решения.

## Модель и измеримые ограничения

- Формат модели: GGUF.
- Целевая модель: `phi-1_5-Q3_K_M`.
- Контекст: постоянный минимум и отдельный рабочий размер для каждого запроса. Для новых настроек минимум 1024, автоматическое увеличение включено, максимум 8192 токена; сохранённый минимум не перезаписывается рабочим размером. Ступени контекста/максимального ответа: 1024/512, 2048/1024, 4096/2048, 8192/4096.
- Перед генерацией токенизатор выбранной GGUF считает окончательную строку запроса: системный текст, шаблон, пользовательский ввод и выбранную историю. Требование: `promptTokens + maxTokens + reserveTokens <= workingContext`. Для нового сообщения до 322 токенов включительно технический запас равен 32, для более длинного сообщения или отсутствующего отдельного замера — 128. Размер сообщения измеряется отдельно только для выбора режима и не прибавляется к полному промпту. При следующем запросе рабочий размер возвращается к минимуму, если весь запрос снова помещается.
- Максимальная длина пользовательского сообщения: 3000 символов по умолчанию; пользователь может установить 500–12000. Текстовый и голосовой ввод используют один параметр выбранной модели. Счётчик сохраняет семантику Kotlin `String.length` (единицы UTF-16).
- Максимальная генерация в чате: половина рабочего контекста, автоматически 512–4096 токенов; этот объём полностью резервируется до отправки и уменьшается вместе с контекстом. При контексте 1024 на полный вход остаётся 480 токенов в режиме небольшого сообщения, 384 — в обычном режиме. Внутренние выжимки конференций сохраняют отдельный фиксированный лимит 512 и обычный запас. Подробнее: [Небольшие сообщения](docs/SMALL_MESSAGE_CONTEXT_BUDGET.md).
- Верхняя граница контекста ограничивается настройкой пользователя, метаданными модели и пределом приложения 8192; это не гарантия доступности такого объёма на любом телефоне. При переполнении запрос отклоняется до генерации с сохранением черновика. Детали и проверки: [Автоматический контекст](docs/AUTOMATIC_MODEL_CONTEXT.md).
- GPU layers: 0.
- Количество потоков инференса: `maxOf(1, availableProcessors - 1)`.

`phi-1_5-Q3_K_M` размером около 703 MB несовместима с ограничением общего PSS/RSS процесса менее 200 MB. Поэтому лимит менее 200 MB относится только к managed heap Kotlin/Java. Общий PSS измеряется отдельно и зависит от размера GGUF, KV-cache, страницы памяти ОС и устройства.

## Доставка и хранение модели

GGUF не входит в APK/AAB и не хранится в Git. Файл из `soft/` используется только как локальный источник разработки; правило `soft/*.gguf` уже исключает его из репозитория.

```text
Разработка                                      Production
-----------                                     -----------
soft/phi-1_5-Q3_K_M.gguf                        HTTPS-сервер моделей
            |                                               |
            | adb push                                      | download + SHA-256
            v                                               v
Android/data/<package>/files/models/            filesDir/models/
            |                                               |
            +--------------- ModelProvider ----------------+
                                            |
                                            v
                                     LlamatikEngine
```

### Debug-сборка

- Модель располагается на устройстве в app-specific external storage: `Android/data/com.example.aiassistent1/files/models/phi-1_5-Q3_K_M.gguf`.
- Перед запуском приложения файл передаётся вручную через `adb`. Это не увеличивает размер APK и не заставляет Gradle обрабатывать файл размером 703 MB.
- Для устройства с подключённым ADB использовать команду:

```powershell
adb shell mkdir -p /sdcard/Android/data/com.example.aiassistent1/files/models
adb push .\soft\phi-1_5-Q3_K_M.gguf /sdcard/Android/data/com.example.aiassistent1/files/models/phi-1_5-Q3_K_M.gguf
```

- `DebugModelProvider` проверяет существование, размер и доступность файла, затем возвращает его абсолютный путь. При отсутствии модели он возвращает понятную ошибку с инструкцией загрузить файл, не пытаясь скачать его автоматически.

### Production-сборка

- `RemoteModelProvider` скачивает модель только по HTTPS в `filesDir/models/` - внутреннее хранилище приложения.
- Загрузка ведётся во временный файл `*.part`. После проверки ожидаемого размера и SHA-256 файл атомарно переименовывается в основной GGUF.
- Неполный или некорректный файл удаляется. Движок получает путь только к успешно проверенной модели.
- Источник URL и ожидаемый SHA-256 не являются секретами, но должны поставляться через конфигурацию сборки или удалённый manifest, а не быть захардкожены в UI.
- При нехватке места, ошибке сети или несовпадении хеша UI показывает состояние ошибки и кнопку повторной попытки; приложение остаётся работоспособным без модели.

```kotlin
interface ModelProvider {
    suspend fun getModelPath(): Result<String>
}
```

`LlamatikEngine` зависит только от `ModelProvider`. Переключение между `DebugModelProvider` и `RemoteModelProvider` выполняется одной регистрацией в `AppModule` для соответствующего build variant.

## Метрики производительности

Метрики фиксируются для конкретного устройства, версии Android, типа сборки и выбранной модели.

- Холодный старт приложения: менее 2 секунд, без загрузки модели.
- Первая загрузка модели: отдельная метрика, измеряемая от первой отправки до `ModelState.Ready`.
- Первый токен: менее 500 ms после `ModelState.Ready`; для первой сессии загрузка модели в эту метрику не входит.
- UI не должен блокировать главный поток во время загрузки, инференса, записи Room или потоковой отрисовки.
- Обновления ответа ассистента должны приходить пакетами: первый фрагмент немедленно, последующие по 3-5 токенов или не реже одного раза в 50 ms.

Проверка: Android Profiler для CPU, памяти и startup; Macrobenchmark или Perfetto для startup и первого ответа; Layout Inspector для рекомпозиции списка.

## Контракт доменного слоя

```kotlin
interface LLMEngine : AutoCloseable {
    val state: StateFlow<ModelState>

    suspend fun ensureLoaded(): Result<Unit>
    fun generate(messages: List<ChatMessage>): Flow<String>
    fun cancelGeneration()
    fun updateParams(params: GenerationParams)
    fun unload()
    override fun close()
}

sealed interface ModelState {
    data object Unloaded : ModelState
    data object Loading : ModelState
    data object Ready : ModelState
    data class Error(val message: String) : ModelState
}

interface InputProvider {
    fun observeInput(): Flow<String>
    fun start()
    fun stop()
}
```

`generate` выдаёт только текстовые дельты в исходном порядке. Для такого потока запрещено использовать `conflate()`, поскольку он может отбросить часть ответа. У каждого `ChatMessage` создаётся неизменяемый ID до добавления в UI; генерация ID внутри ключа `LazyColumn` запрещена.

## LLM-движок

LLM-слой использует `com.llamatik:library:1.7.0` из Maven Central. Llamatik уже поставляет Android-интеграцию с `llama.cpp` (версия `b9574`), поэтому отдельная зависимость, исходный код или JNI-обёртка `llama.cpp` в проект не добавляются. Это исключает дублирование нативных библиотек и конфликты ABI.

Публичный API для реализации: `LlamaBridge.initGenerateModel`, `LlamaBridge.generateStream`, `LlamaBridge.updateGenerateParams` и `LlamaBridge.shutdown`. Перед обновлением Llamatik проверить release notes и при необходимости адаптировать `LlamatikEngine` к изменённому API.

- Модель загружается лениво в `ensureLoaded()` при первой отправке сообщения.
- Состояние загрузки защищается `Mutex`, чтобы параллельные отправки не запускали две загрузки.
- Загрузка файла выполняется на `Dispatchers.IO`.
- CPU-инференс выполняется на выделенном dispatcher с ограниченным числом потоков. `unload()` выгружает модель с сохранением executor для повторной загрузки. `close()` окончательно закрывает экземпляр и освобождает dispatcher, в том числе при ошибке нативной очистки.
- Если callback нативной библиотеки не suspend, отправлять фрагменты в `Flow` через `trySend`, а не через suspend-вызов `send`.
- Первый фрагмент отправлять немедленно. Затем копить 3-5 токенов или сбрасывать буфер по таймауту 50 ms. Всегда отправлять остаток буфера при обычном завершении.
- `cancelGeneration()` обязан передавать отмену в нативную генерацию через поддерживаемый API либо потокобезопасный флаг, который проверяется callback-ом.
- При `OutOfMemoryError` освободить нативные ресурсы, установить `ModelState.Error("Недостаточно памяти для модели")` и вернуть ошибку без падения приложения.
- При ошибке загрузки или генерации приложение остаётся доступным: пользователь видит сообщение об ошибке и может повторить попытку.

Контракт жизненного цикла уточнён 28 сентября 2026 года: при смене модели и до/после выжимки применяется `unload()`, при уничтожении `ChatViewModel` — `close()`. Обоснование, поведение закрытого экземпляра, карта конфликтов между сценариями и результаты проверок: [LLM_ENGINE_LIFECYCLE.md](docs/LLM_ENGINE_LIFECYCLE.md). Эта запись уточняет жизненный цикл; остальные исторические параметры спецификации ею не актуализируются.

## Room и история чата

- Использовать Room для постоянной истории сообщений.
- Создать `ChatMessageEntity`, `ChatMessageDao`, `ChatDatabase` и mapper между entity и domain model.
- Явно задать версию схемы базы.
- Для каждого изменения схемы добавлять SQL-миграцию и migration test. На первой версии базы миграция не требуется.
- История загружается в `ChatViewModel` при создании.
- Сообщение пользователя сохраняется до запуска генерации. Полный ответ ассистента сохраняется после завершения; при отмене сохраняется уже полученный текст с признаком `isInterrupted`.
- Операции Room выполнять на `Dispatchers.IO`.

## ChatViewModel и состояние

`ChatViewModel` получает use case и `LLMEngine` через конструктор. `ModelState` движка объединяется с состоянием экрана через `combine`, поэтому UI всегда отражает фактический статус модели.

- Пустые сообщения, строки длиннее настроенного лимита (по умолчанию 3000 символов) и повторная отправка во время обработки отклоняются. Переполнение контекста проверяется отдельно в токенах до записи нового сообщения в историю; введённый текст сохраняется.
- В состоянии `Unloaded` поле ввода активно: первая отправка запускает `ensureLoaded()` и показывает загрузку.
- В состоянии `Loading` и во время генерации повторная отправка отключена, кнопка остановки доступна только при генерации.
- Сообщение пользователя добавляется в UI сразу.
- Временное сообщение ассистента создаётся с постоянным ID до начала получения дельт.
- При `CancellationException` не добавлять второе системное сообщение: обновить уже существующий ответ флагом прерывания и завершить `isProcessing`.
- В `onCleared()` остановить генерацию и голосовые ресурсы, затем окончательно закрыть LLM через `llmEngine.close()`. Одна отмена или `unload()` не завершает executor. Обычный переход в фон не является уничтожением ViewModel.

## Compose UI

- Основной экран: `ChatScreen`, `MessageList`, `MessageBubble`, `InputPanel`, `ModelStatusIndicator`.
- Использовать `LazyColumn` с ключом `key = { message.id }`.
- Список не должен пересоздаваться для каждого фрагмента ответа: обновлять только сообщение ассистента с тем же ID.
- Автопрокрутку выполнять только когда пользователь находится у нижней границы списка. Во время генерации использовать `scrollToItem`, чтобы не запускать анимацию на каждый пакет токенов.
- Ошибки показывать через `SnackbarHost` и оставлять экран пригодным для следующей отправки.
- Кнопки голоса, календаря и агента добавлять в UI невидимыми до реализации: `visible = false`.

## Заглушки будущих функций

Каждая будущая функция сначала получает интерфейс в `domain/interfaces`, реализацию в `data` и регистрацию в `AppModule`.

```kotlin
/** [ЗАГЛУШКА] Голосовой ввод будет реализован в версии 1.1. */
class VoiceInputProvider : InputProvider {
    override fun observeInput(): Flow<String> = emptyFlow()
    override fun start() = Unit
    override fun stop() = Unit
}
```

Аналогично создать `StubCalendarProvider` и `StubAgentTool`. Они не запрашивают разрешения, не выполняют I/O и не влияют на запуск приложения.

## Правила реализации и проверки

1. Перед добавлением Llamatik подтвердить API выбранной версии и добавить минимальный integration test загрузки модели.
2. Проверять `SendMessageUseCase`, `ChatViewModel`, ошибки загрузки, отмену, настраиваемую длину сообщения и вместимость всего запроса. Для автоматического контекста обязательны проверки увеличения, возврата к минимуму, сохранения истории и отказа при превышении максимума.
3. Добавить Room migration test при появлении второй версии схемы.
4. Проверить, что модель не создаётся при холодном старте и до первой отправки.
5. Проверить обработку отсутствующего файла модели, ошибки загрузки, OOM и отмены без падения процесса.
6. Измерить startup, первую загрузку, первый токен, PSS и число рекомпозиций на целевом устройстве.

## Критерий готовности MVP

MVP считается готовым, когда приложение собирается, открывает историю из Room, позволяет отправить текст, лениво загружает подтверждённую GGUF-модель, потоково отображает полный ответ без потери дельт, корректно отменяет генерацию и сохраняет работоспособность при ошибках.
