# Максимальный размер модели по доступной памяти

Дата: 2026-10-03.

## Что видит пользователь

В настройках «Модель», рядом с доступной RAM, добавлено описание:

> Расчётный максимальный размер модели: до X ГБ при контексте N токенов.
> Оценка размера файла GGUF для параметров выбранной модели.

X — рассчитанный размер файла, N — текущий контекст. Значение пересчитывается сразу при редактировании контекста или Batch Size, после выбора модели и при очередном обновлении RAM. Соотношение 2:1 / 4:1 само по себе не меняет оценку. Единицы десятичные: 1 ГБ = 1 000 000 000 байт. Подпись округляется вниз до двух знаков; для небольших размеров используются МБ, КБ или байты.

Если выбранная модель слишком велика и шкала контекста отключена, оценка показывается при минимальном контексте (обычно 512), с явной подписью «при минимальном контексте». Это позволяет оценить подходящий размер файла меньшей модели. При недоступных показаниях RAM или неподдерживаемых метаданных числовой максимум не показывается. Если рабочие буферы исчерпывают бюджет, выводится сообщение о нехватке памяти.

## Расчёт

Используется бюджет из существующего `ModelMemoryCalculator`: доступная память за вычетом резерва системы/приложения, с прежним учётом приватных буферов уже загруженной модели и ограничением для 32-битного процесса.

1. Для выбранного контекста вычисляются KV-кеш, активации, логиты, рабочее место attention и служебный резерв. Их стоимость вычитается из бюджета.
2. Двоичный поиск находит наибольший размер файла, для которого хватает остатка: `размер × число копий + max(64 МиБ, размер / 10)`. Число копий — 1 без GPU-слоёв, иначе 2.
3. Стоимость весов вычисляется той же функцией, которую использует ограничение контекста. Существующий файл повторно не вычитается из остатка. Арифметика проверяется на переполнение.

Размеры слоёв, голов и других буферов берутся из выбранного GGUF. Поэтому результат относится к этим параметрам и текущему контексту; это не универсальный предел для всех файлов GGUF одинакового размера и не гарантия отсутствия OOM.

## Почему так лучше

Пользователь получает размер в привычных единицах вместе с контекстом, для которого он рассчитан. Один общий расчёт исключает расхождение между описанием и потолком контекста. Округление вниз не завышает подпись. При движении ползунков расчёт использует текущие значения редактора без ожидания записи DataStore и без чтения файлов или Android API в главном потоке.

Бюджет и метаданные для описания остаются временными данными: в DataStore они не сохраняются. Обновление RAM само по себе не вызывает сохранения настроек. Проверка непосредственно перед native-загрузкой остаётся независимой от описания.

## Проверки

Добавлены 11 JVM-тестов: точная граница вместимости, обе ветви накладных расходов, GPU-копия, контекст/batch, резерв и учёт загруженной памяти, переполнения Long, форматирование без округления вверх, немедленное обновление текста, отсутствие лишней записи настроек и обработка недоступных данных. Проверка guard дополнена сравнением бюджета до и после загрузки.

Итог проверки:

- `:app:testDebugUnitTest`: 486 тестов, 0 ошибок, падений и пропусков.
- `:app:assembleDebug`: APK собран. NDK `llvm-strip` сообщил `Permission denied`; Gradle включил `libassistant_audio.so`, `libassistant_metric_kws.so`, `libc++_shared.so` и `libmp3lame.so` без удаления отладочных символов.
- `:app:lintDebug`: 0 ошибок, 42 предупреждения и 2 подсказки.
- `git diff --check` прошёл. Шесть Kotlin-файлов этого дополнения не изменялись во время итогового запуска тестов, сборки и lint.

APK не устанавливался. Проверка интерфейса, потребления памяти и GGUF-инференса на физическом телефоне не выполнялась.
