# Раздельные настройки моделей календаря и чата

Дата: 2026-10-01.

## Поведение

В разделе настроек «Модель» находятся вкладки «Модель календарь» и «Модель чат». Каждая редактирует свой набор параметров для выбранного файла модели. Переключение вкладки настроек не меняет режим разговора.

| Параметр | Модель календарь | Модель чат |
| --- | --- | --- |
| Размер вопроса, токены | 512 | 2048 |
| Место под ответ, токены | 256 | 1024 |
| Temperature | 0.36 | 0.70 |
| Top P | 0.90 | 0.80 |
| Top K | 20 | 20 |
| Repeat Penalty | 1.15 | 1.15 |
| Batch Size | Авто: 256 | Авто: 512 |
| Потоки CPU | Авто, по числу доступных процессоров | Авто, по числу доступных процессоров |

На шкалах отмечены значения по умолчанию выбранного профиля. Дробные значения подписаны с двумя знаками после точки. Top K изменяется от 1 до 100 с шагом 1 и меткой 20. Batch Size имеет режимы «Авто» и «Вручную», подробнее — в `MODEL_BATCH_SIZE.md`. Настройка «Потоки CPU» использует такие же режимы, ручную шкалу 1..N и метку автоматического значения; подробнее — в `MODEL_CPU_THREADS.md`.

«Контекст» переименован в «Размер вопроса». Это название общего окна модели, которое включает место под ответ, а не отдельный лимит только входного текста. Максимум теперь определяется по `[архитектура].context_length` выбранного GGUF. При неизвестном значении остаётся потолок приложения 8192. Обычно размер вопроса начинается с 512 и изменяется с шагом 512; ответ — с шагом 256. Потолок округляется вниз до допустимой позиции. Для предела меньше 512 используется одна доступная чётная позиция. Движение любой из этих шкал сразу обновляет оба значения с точным соотношением 2:1. Подробности — в `MODEL_GGUF_CONTEXT_LIMIT.md`.

Под шкалами показан текст:

> Размер вопроса к модели включает в себя зарезервированное место под ответ. Настройки синхронизируются: под ответ выделяется половина размера вопроса. Если ответ модели не поместился в карточке ответа, увеличьте место под ответ.

## Хранение и совместимость

Ключи DataStore имеют вид `model_params/calendar/<имя модели>/<параметр>` и `model_params/chat/<имя модели>/<параметр>`. Все параметры профиля, включая режимы и ручные значения Batch Size и потоков CPU, сохраняются одной транзакцией. Другой профиль и другие файлы модели сохраняют собственные настройки.

Старые общие ключи `<имя модели>_<параметр>` читаются только как резервные значения календаря, пока соответствующий новый ключ отсутствует. Профиль чата начинает с новых значений по умолчанию. Чтение не перезаписывает старые ключи. Следующее сохранение календаря записывает полный набор в новые ключи.

Сохранённый размер вопроса ограничивается диапазоном и округляется к шагу 512, ответ рассчитывается как половина. Top K ограничивается диапазоном 1–100; ручной Batch Size приводится к допустимой позиции шкалы; число потоков CPU — к диапазону 1..N доступных процессоров. Остальные ранее сохранённые значения сохраняются. Новые значения по умолчанию не сбрасывают пользовательские настройки календаря.

Поток параметров выдаёт первое значение после чтения DataStore и метаданных файла модели. Пока чтение не завершено, интерфейс показывает загрузку вместо доступных для редактирования временных значений. Метаданные не сохраняются как пользовательский параметр: при записи предел заново определяется для целевого файла.

## Применение и время жизни

Изменённые параметры сохраняются каждые 1000 мс, пока нужная вкладка открыта, раздел «Модель» раскрыт и приложение находится в состоянии RESUMED. Непрерывное движение ползунка не перезапускает интервал. Неизменённые значения повторно не записываются.

При переключении вкладки, сворачивании раздела, закрытии диалога или выходе из RESUMED прежний таймер отменяется, а последнее несохранённое изменение отправляется на сохранение сразу. Это разовое сохранение может произойти раньше следующей секунды. Запись выполняется через ViewModel; имя модели и профиль фиксируются в callback. Отдельное состояние редактора каждого профиля сохраняет правки при переключении вкладок и защищает их от запоздавших уведомлений DataStore.

Обычный запрос применяет профиль режима разговора: календарь или чат. Перед запросом читаются сохранённые параметры; записи из интерфейса и чтение перед запросом сериализованы. Форматирование поля календарного черновика использует профиль календаря. Когда движок свободен, изменения активного профиля применяются после сохранения. Во время ответа, остановки генерации или суммаризации обновления из настроек не заменяют параметры выполняющегося запроса; они применяются после его завершения.

Изменённые Batch Size, размер контекста, фактическое число потоков CPU и GPU-слои требуют повторной загрузки перед следующим запросом. Сохранение настроек не запускает её само по себе. Суммаризация конференций запрашивает временное окно 4096/512, ограниченное пределом файла модели, и затем возвращает профиль текущего режима. Перед загрузкой движок независимо читает GGUF и ограничивает передаваемые в native параметры. Временная выгрузка модели использует `unload()`, окончательное закрытие остаётся у владельца движка.

## Почему так

Раздельные профили позволяют менять параметры чата и календаря независимо. Привязка к режиму запроса устраняет зависимость генерации от последней открытой вкладки настроек. Атомарная запись и связь шкал исключают несовместимые сохранённые пары. Таймер ограничивает частоту записи и прекращает периодическую работу при закрытии вкладки.

Соотношение задаёт максимальный лимит генерации, а не обязательную длину ответа. Сборка prompt и код библиотеки Llamatik не изменены; отдельная обрезка входного prompt по токенам не добавлена. Проверка статуса «Работа во сне» остаётся отдельной с интервалом 500 мс.

## Проверки

JVM-тесты проверяют значения по умолчанию, диапазоны и пересчёт шкал, совместимость старых настроек, изоляцию профилей и моделей, атомарную запись, восстановление обоих профилей из настоящего файла DataStore и ожидание чтения хранилища. Тесты контроллера проверяют выбор активного профиля, отложенное применение во время ответа и суммаризации. Тесты виртуального времени проверяют секундный интервал, завершающую запись, повторное открытие и отсутствие лишних записей.

Результаты тестов, сборки и lint фиксируются в итоговом отчёте задачи. Эти проверки не заменяют проверку интерфейса и GGUF-инференса на физическом устройстве.
