# Часовые пояса календаря

Дата: 20 октября 2026 года.

Единая политика времени согласует календарь, ввод, поиск и подсчёт сумм после смены пояса. Закрепление пояса за незавершённой операцией защищает уже введённое расписание от незаметной переинтерпретации.

## Поведение

- При первом запуске приложение запоминает пояс телефона и автоматически следует ему.
- После обнаруженной смены пояса появляется авторский значок: глобус с часами. Точка на значке обозначает ещё не подтверждённое изменение.
- Нажатие открывает список доступных системных часовых поясов с поиском по городу, идентификатору или смещению UTC. Города локализуются средствами Android; российские города имеют явные русские названия.
- «Часовой пояс телефона» включает автоматический режим. Выбор конкретного пояса закрепляет его для календаря, включая новые запросы и события.
- Выбор сохраняется после закрытия приложения. После первого обнаруженного изменения значок остаётся доступным для последующего выбора.
- При закреплённом поясе очередная смена пояса телефона показывает отметку на значке, но сохраняет выбранный пользователем пояс календаря.

В автоматическом режиме смена Самары на Москву показывает встречу 20 октября 2026 года в 15:00 по Самаре как 14:00 по Москве. Момент встречи остаётся прежним. Событие около полуночи может отображаться в другом календарном дне или месяце.

## Сохранность событий

`CalendarTimeZoneRepository` управляет только политикой времени и её настройками. Он не имеет доступа к репозиторию событий.

Смена пояса и выбор в списке не выполняют создание, изменение или удаление событий. Существующие `startsAtEpochMillis` и `endsAtEpochMillis` остаются прежними. Схема Room, версия календарной базы и сохранённые записи не мигрируют.

Границы запроса месяца, группировка по дням, счётчики, переход к сохранённому событию, поиск и сумма рассчитываются с учётом выбранного пояса. Выбранные месяц и день при смене пояса не сбрасываются. Сумма за конкретную местную дату может измениться: в разных поясах один UTC-момент попадает в разные сутки.

Обычное редактирование события по-прежнему может изменить его расписание по действию пользователя. Редактирование только названия, ценности или примечания сохраняет исходные метки времени, в том числе для ранее сохранённого неоднозначного времени при осеннем переводе часов.

## Запросы к модели

Перед запросом фиксируются момент и выбранный пояс. Один контекст применяется к местным дате/времени системного сообщения, проверке ответа, преобразованию периода, поиску и сохранению черновика.

Модель получает только прежний формат местных даты, времени и дня недели. Идентификатор пояса, смещение UTC и новые поля JSON ей не передаются. Контракт календарных команд сохранён.

Если пояс изменился во время генерации, полученный черновик сохраняет исходную интерпретацию. Результат поиска или суммы относится к поясу запроса. Региональные подписи остаются только в элементах интерфейса: приложение не дописывает пояс в сохраняемый текст ответа, который затем мог бы попасть в историю следующего запроса к модели. История сообщений не переписывается.

## Черновики и редактор

Новые черновики сохраняют `timeZoneId` и `timeZoneConfirmedFor` в существующем DataStore-формате. Отсутствующие поля старых записей читаются как неизвестный пояс; текущий пояс не выдаётся за исторический.

Если пояс изменился, перед новым сохранением доступны два явных действия:

1. «Сохранить прежний момент» — введённые значения продолжают интерпретироваться в исходном поясе.
2. «Считать введённое время по поясу: …» — те же введённые дата и время интерпретируются в текущем выбранном поясе. Это осознанный выбор другого момента для несохранённого расписания.

У старого черновика без известного пояса доступно подтверждение текущего пояса. Новый черновик нельзя сохранить, пока эта неопределённость не разрешена.

Начатое сохранение сохраняет свой пояс и `requestId` для повторной проверки результата. Для старого прерванного сохранения без пояса сначала проверяется квитанция: уже созданное событие повторно не создаётся. Если квитанции нет, черновик снова становится редактируемым и требует подтверждения пояса.

Открытый ручной редактор сохраняет пояс и дату открытия. Смена пояса телефона не переинтерпретирует его поля. Перед сохранением пользователь подтверждает прежний момент либо выбирает новый пояс для введённых значений.

## Переходы часов

Используются правила `ZoneId` для даты события. Смещение в списке показано на текущую дату и не применяется как постоянная числовая поправка ко всем событиям.

Длительность и окончание рассчитываются по фактически прошедшим минутам. Несуществующее или неоднозначное новое местное время отклоняется существующим `CalendarTime`, включая ручной ввод. Произвольный выбор одного из двух UTC-моментов не выполняется.

В этом изменении не вводятся события «всегда в 09:00 по местному времени», повторения, события на весь день и планировщик уведомлений.

## Обнаружение смены пояса

Общий поставщик реагирует на системное `ACTION_TIMEZONE_CHANGED`, запуск и возвращение приложения на экран. Последний известный пояс сохраняется, поэтому доступно обнаружение изменения, произошедшего при закрытом приложении. До первого запуска этой функции исторический пояс неизвестен.

Системный сигнал минуты обновляет подписи и проверяет смену даты в выбранном поясе; постоянного фонового опроса нет. Дата календаря может смениться в другое время, чем дата телефона при ручном выборе другого пояса.

## Проверки

Команда сборки и проверки:

```powershell
.\gradlew.bat test :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug --console=plain --quiet
```

- Модульные тесты: 778 всего; 777 прошли, ошибок нет, 1 пропущен. По модулям: `app` — 757, `calendar-core` — 11, `calendar-storage-android` — 10.
- Пропущен существующий внешний `CalendarPromptContractTest`: для него не задан каталог завершённой оценки `CALENDAR_PROMPT_EVALUATION`. Это не подтверждение качества реальной GGUF-модели.
- APK приложения и тестовый APK собираются. `lintDebug` завершается без ошибок; предупреждения доступны в штатном отчёте `app/build/reports/lint-results-debug.html`.
- Проверены смена Самара ↔ Москва, восстановление выбора, ошибка записи настроек, границы суток/месяца, переходы DST, неизменность контекста запроса, обязательное подтверждение старого черновика и квитанции повторного сохранения.
- Передаваемый модели текст проверяется через `SystemPromptProvider` и фактический `SendMessageUseCase` с тестовым движком. Часовой пояс в системное сообщение не добавляется.

- UI и интеграция: **12 тестов прошли** на отдельном эмуляторе Android 14 / API 34 / x86_64. Серия: `CalendarTimeZoneUiTest`, `CalendarEventEditorDialogTest`, `CalendarDraftCardsTest`, `CalendarTimeZoneAppTest`.
- Настоящая смена системного пояса через `AlarmManager` обновляет интерфейс без перезапуска. Проверены появление значка, поиск в списке, ручной выбор и возврат к поясу телефона.
- Интеграционный тест открывает настоящий `CalendarScreen` с `CalendarViewModel` и изолированной Room-базой: Самара 15:00–16:00 превращается в Москва 14:00–15:00. Полное сравнение сохранённого события до/после подтверждает неизменность обеих UTC-меток, названия, примечания, ценности, ревизии и служебных дат.
- Обычный холодный запуск APK и переход «разговор → календарь → разговор» дополнительно проверены через реальный интерфейс приложения вне Compose-тестового правила.
