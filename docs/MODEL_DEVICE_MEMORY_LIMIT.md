# Контекст по RAM и выбор 2:1 / 4:1

Дата: 2026-10-02.

## Что изменилось

В разделе «Модель» добавлен выбор **2:1 / 4:1**, отдельно для файла модели и профиля «Модель календарь / Модель чат». По умолчанию остаётся 2:1. При контексте 4096 это 2048 или 1024 токена под ответ. Переключение сохраняет допустимый контекст и пересчитывает ответ, его шкалу, метку и пояснение. Общий контекст уже включает ответ.

Максимум шкалы — меньшее из предела GGUF и расчётного предела RAM, округлённое вниз до шага 512. Текущее значение ограничивается максимумом, но автоматически не увеличивается до него. Показаны доступная и общая RAM, предел модели и результат расчёта. Чистые mmap-страницы уже могут входить в `availMem`; это не только физически пустая память.

Соотношение, контекст и ответ сохраняются одной транзакцией DataStore. Отсутствующее или неизвестное соотношение читается как 2:1. Вкладка настроек не меняет режим разговора. Изменения во время ответа применяются после текущего запроса; при изменении фактического batch движок пересоздаёт native-контекст перед следующим запросом.

## Расчёт памяти

Используются `ActivityManager.MemoryInfo` (`totalMem`, `availMem`, `threshold`, `lowMemory`), private-dirty память собственного процесса и его разрядность. Из GGUF читаются размер файла, архитектура, число слоёв, embedding, feed-forward, головы attention/KV, размеры K/V и vocabulary. При отсутствии `vocab_size` используется число токенов `tokenizer.ggml.tokens`; при наличии обоих берётся большее. Массив токенизатора не загружается в память.

Резерв: `max(768 МиБ, 20% totalMem, threshold) + 256 МиБ`.

Оценка затрат:

| Часть | Формула |
| --- | --- |
| Веса | Размер GGUF + max(64 МиБ, 10% размера); при GPU-слоях ещё размер файла под возможную копию |
| KV-кеш | layers × kv_heads × (key_length + value_length) × 4 × context |
| Активации | batch × (12 × embedding + 4 × feed_forward) × 4 |
| Логиты | batch × vocabulary × 4 |
| Рабочее место attention | batch × heads × context × 4 |
| Дополнительный резерв | 128 МиБ |

Контекст для буферов округляется вверх до 256. Четыре байта на K/V — оценка вплоть до FP32, а не утверждение о фактическом типе кеша Llamatik. Рабочее место attention резервируется и на случай недоступности Flash Attention.

В оценщике автоматический batch равен `min(512, context)`; ручной учитывается по допустимому размеру. Он не получает соотношение или `maxTokens`: ответ не прибавляется к контексту повторно. Поэтому переключение 2:1 → 4:1 не меняет потолок RAM и покрыто запасом даже при росте фактического batch, например 256 → 384 для контекста 512.

Двоичный поиск выбирает наибольший шаг 512, помещающийся после резерва. Для 32-битного процесса бюджет дополнительно ограничен 768 МиБ. Переполнения арифметики проверяются.

Поддерживаются скалярные размеры `llama`, `qwen2`, `qwen3`, `gemma`, `gemma2`, `gemma3`, `phi2`, `phi3`. Гибридные, MLA и другие архитектуры требуют отдельного оценщика. Отсутствующие необязательные KV-размеры получают значения по спецификации GGUF; некорректные присутствующие поля не заменяются значениями по умолчанию. При неподдерживаемых/недостаточных метаданных загрузка приостанавливается с объяснением. Чтение самого `context_length` не ограничено списком оценщика.

## Обновление и защита

Проверка выполняется вне главного потока при чтении/сохранении профиля, перед загрузкой и повторным использованием модели; после выгрузки старой модели RAM проверяется снова. Во время раскрытого раздела «Модель» в RESUMED показания обновляются каждые пять секунд. UI не может подменить доверенный предел.

Для загруженной модели прибавляется обратно измеренный прирост resident private-dirty памяти процесса, ограниченный расчётным объёмом приватных буферов модели. Это приближённый учёт: другие выделения того же процесса неотделимы от него. Чистые mmap-страницы весов не прибавляются обратно. После выгрузки/ошибки запись сбрасывается.

При `lowMemory`, недоступных показаниях или нехватке RAM даже для контекста 512 загрузка блокируется, шкалы контекста/ответа отключаются. Временный нулевой предел не затирает последнюю пригодную пару в DataStore и ручной Batch Size. Новое соотношение можно сохранить и в этом состоянии. После восстановления RAM параметры снова ограничиваются свежим пределом. Сам опрос памяти не сохраняет уменьшенный контекст.

## Почему так лучше и границы проверки

GGUF задаёт предел модели, RAM — текущие возможности устройства. Раздельные ограничения сохраняют независимость выбора ответа. Проверка перед загрузкой учитывает устаревшие настройки и временные профили. Запас снижает риск нехватки памяти, но не гарантирует отсутствие OOM, завершения процесса Android или приемлемую скорость: это требует проверки выбранной модели на телефоне.

Добавлены JVM-проверки формулы, граничных значений, GGUF, учёта загруженной памяти, обоих соотношений, сохранения/восстановления DataStore и повторной проверки движком. Native-вызовы в JVM-тестах заменены тестовым runtime; это проверка Kotlin-интеграции, а не GGUF-инференса.

Проверка 2026-10-02:

- `:app:testDebugUnitTest`: 475 тестов, включая 31 новый; 0 ошибок, падений и пропусков.
- `:app:assembleDebug`: APK успешно собран.
- `:app:compileDebugAndroidTestKotlin`: инструментальные тесты скомпилированы; на устройстве не запускались.
- `:app:lintDebug`: 0 ошибок, 42 предупреждения и 2 подсказки.
