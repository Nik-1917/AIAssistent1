## Порядок выполнения

1. Установка переносимого Restic и контроллера в `C:\ProgramData\ProfileBackup007`. Скрипты и EXE доступны для изменения только Administrators и SYSTEM, поэтому обычный процесс пользователя не может заменить код задания SYSTEM.
2. Создание нового репозитория формата 2 и отдельного каталога восстановления. Существующие каталоги установки, репозитория и задания с совпавшими именами не перезаписываются.
3. Пробный запуск полного профиля через VSS с `--dry-run` и максимальным сжатием. Он читает и сжимает данные для расчёта, но не записывает содержимое файлов в репозиторий. Успешным считается только код 0; код 3 означает неполную доступность исходных данных и не позволяет заявить об успешном резерве.
4. Если измеренный объём укладывается с запасом, полное резервирование. Во время работы проверяется свободное место: остановка собственного процесса при достижении 11 ГиБ даёт дополнительный буфер к согласованному минимуму 10 ГиБ. Между пробой и записью профиль может измениться; контроль места сохраняется во время записи.
5. `restic check --read-data` читает и проверяет всё содержимое репозитория. Затем отдельное восстановление четырёх GGUF V12.66 и выбранных небольших файлов выполняется в новой тестовой папке ProgramData, с `--verify` и сравнением SHA-256 моделей с ранее проверенными суммами. Тест не восстанавливает файлы поверх исходного профиля. Созданные тестовые копии удаляются только в проверенной собственной тестовой папке, без перехода по reparse point.
6. Только после успешной первой копии и проверок создаётся `ProfileBackup007-Hourly`. Повтор — один час, запускается от SYSTEM, одновременно выполняется только одно задание. При выключенном компьютере резервирование не выполняется; предусмотрен запуск пропущенного задания после доступности системы. Каждое обновление имеет предварительный расчёт места, структурную проверку и SHA-256 вновь записанных pack-файлов.

Источники не удаляются. Автоматические `forget`/`prune` не включены: предыдущие снимки сохраняются. При нехватке места задание сообщает ошибку и сохраняет имеющиеся снимки; оно не освобождает место удалением пользовательских данных.

## Специальные объекты Windows

Дополнительная проверка через `FSCTL_GET_REPARSE_POINT` определила 115 объектов профиля: 24 junction, 86 `APPEXECLINK` и 5 `AF_UNIX`. У 24 распознанных junction цели находятся внутри профиля. Псевдонимы приложений и сокеты имеют нулевую логическую длину; они содержат специальные метаданные Windows. Это не доказательство восстановления установленных программ или активных соединений.

Restic 0.19.1 не сохраняет `APPEXECLINK` как обычные файлы: реальная проба WindowsApps вернула код 3 и `unsupported file type "irregular"`. Контроллер дополнен отдельным захватом сырых метаданных reparse points. Из обычного копирования точечно исключаются только подтверждённые нулевые `APPEXECLINK` и `AF_UNIX`; остальные файлы остаются включёнными. Для объекта с ненулевой длиной такое исключение запрещено.

Манифест сырых метаданных `C:\ProgramData\ProfileBackup007\source-metadata\profile-special.json` добавляется в тот же зашифрованный снимок вместе с профилем. Поэтому снимок содержит ещё один собственный служебный файл вне папки пользователя. После восстановления его SHA-256 сравнивается с исходным манифестом. Проба в Windows PowerShell 5.1 сохранила сведения о всех 115 объектах, прошла `check --read-data`, восстановление `--verify` и сравнение SHA-256; исходные объекты не изменялись. Работоспособность псевдонимов после переустановки приложений этим тестом не подтверждается.

Полный предварительный проход завершён прежним контроллером. Измерение повторно использовано после строгой классификации всех ошибок: обнаружены исключительно ошибки известных `APPEXECLINK`, итоговый отчёт полный, область данных репозитория оставалась пустой. Проверенное доказательство сохранено в `C:\ProgramData\ProfileBackup007\measured-probe.json`. Любая ошибка обычного файла или неизвестного объекта запретила бы такой переход. Исправление рабочего скрипта применялось после окончания прежнего процесса. Новая полная копия должна завершиться кодом 0; неполная копия успешной не считается.

Для полного обхода закрытых каталогов сборщик метаданных дополнен `SeBackupPrivilege`, открытием каталогов только для чтения с `FILE_FLAG_BACKUP_SEMANTICS` и перечислением через `GetFileInformationByHandleEx`. Эти средства [предусмотрены Microsoft для резервирования объектов с ограничивающими ACL](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights). Обход не переходит по reparse points и не меняет права источника; неизвестные ошибки чтения останавливают работу. Проверка в Windows PowerShell 5.1 сравнила имена, атрибуты и длины с обычным перечислением в трёх реальных каталогах, включая WindowsApps и каталог VS Code: совпадение полное. Отдельное защищённое задание проверило полный сбор от SYSTEM и чтение ранее закрытого каталога; результат `Passed = true` сохранён в `C:\ProgramData\ProfileBackup007\native-capture-verification.json` (15:34 UTC).

## Ключ и восстановление после отказа C:

Ключ создаётся криптографическим генератором. Локальная копия — DPAPI LocalMachine в закрытой папке ProgramData; ключ восстановления — `D:\Backups\007-restic-recovery\password.key`. Там же находятся переносимый `restic.exe`, инструкция `RECOVERY.txt` и записи об успешно проверенных снимках. Пароль не выводится в чат, командную строку или отчёт.

NTFS-доступ к репозиторию и каталогу восстановления ограничивается исходным пользователем, Administrators и SYSTEM. Ключ хранится на том же HDD отдельно от репозитория: это обеспечивает восстановление после потери C:, но не защищает данные от человека, который способен прочитать весь HDD вместе с ключом. Для независимого хранения ключа можно сделать его отдельную офлайн-копию.

Это резерв файлов профиля, а не образ Windows. Полное восстановление Windows, установленных приложений, работающих виртуальных машин и учётных данных приложений данным тестом не подтверждается. VSS имеет собственные правила исключения файлов; их ограничения нужно учитывать при оценке полноты.

```powershell

Общий `PASSED` и пустой журнал ATA-ошибок не объясняют рост этого показателя. Нормализованные 86 у ATA 9 также не означают 86% оставшегося ресурса.

Интерфейсные CRC-ошибки являются основанием проверить соединение диска. Разработчик smartmontools [объясняет связь таких ошибок с кабелями и разъёмами](https://sourceforge.net/p/smartmontools/mailman/message/10779977/). Практический следующий шаг — проверить SATA-подключение Toshiba при полностью выключенном компьютере, затем повторно сравнить показатель. Неисправность конкретного кабеля, контроллера или самого HDD этой проверкой не установлена. Для защиты данных требуется дополнительная независимая копия; текущий Toshiba не следует считать единственной достаточной защитой.
