# OpenCL на Redmi Note 11E Pro

19 ноября 2026 года диагностическая сборка Android-приложения выполнила генерацию Qwen3-0.6B V12.67 через OpenCL на физическом Redmi Note 11E Pro. Проверены два файла GGUF, Q8_0 и Q4_K_M, с частичной и полной выгрузкой слоёв. В той сборке обычный режим «Авто» использовал Vulkan или CPU. 20 ноября OpenCL подключён к обычной генерации и отдельному пункту «Настройки → Вычисления AI». [Отчёт об интеграции](LLM_OPENCL_AUTOMATIC_ANDROID.md) · [План и лицензии](LLM_OPENCL_ANDROID_PLAN.md) · [Измерения 19 ноября](validation/LLM_OPENCL_REDMI_2026_11_19.json)

## Что выполнял телефон

Redmi с Android 13, API 33 и прошивкой V14.0.6.0.TKCMIXM открыл системную `/vendor/lib64/libOpenCL.so` из процесса приложения `:llm`. Драйвер сообщил Adreno 619, OpenCL C 2.0, компилятор E031.38.01.08 и поддержку `cl_khr_fp16`. Пробное ядро вычислило все 16 ожидаемых значений `i*i+7`. SHA-256 обоих GGUF проверены непосредственно на телефоне.

Затем приложение загрузило тот же GGML и те же веса, что использует основной движок. Для каждой модели проверена выгрузка 1/29 и 29/29 слоёв. Счётчик включает 28 блоков и выходной слой. В каждой фазе диагностика дождалась завершения матричного ядра, проверила состояние события `CL_COMPLETE` и тип устройства очереди `CL_DEVICE_TYPE_GPU`. Это подтверждает вычисления при обработке запроса и при генерации токенов. Число 29/29 описывает размещение слоёв модели. Токенизация, выбор следующего токена и часть других операций могут выполняться на CPU.

| Полная выгрузка | Ядро при обработке запроса | Ядро при генерации ответа |
| --- | --- | --- |
| Q8_0 | `kernel_gemm_noshuffle_q8_0_f32` | `kernel_gemv_noshuffle_q8_0_f32` |
| Q4_K_M | `kernel_gemm_noshuffle_q4_k_f32` | `kernel_gemv_noshuffle_q4_k_f32` |

При 29 слоях GGML сообщил размер OpenCL-буфера весов 604,15 МиБ для Q8_0 и 372,65 МиБ для Q4_K_M. Это один из буферов модели. Пиковое потребление памяти всего процесса в этом испытании не измерялось.

Для календаря использована команда «Создай событие с названием Встреча». Обе модели вернули полный JSON с действием `calendar_add` и названием «Встреча». Для каждого файла результат CPU и полной выгрузки OpenCL совпал посимвольно. Испытание заканчивается разбором команды. Записи в пользовательский календарь оно не создаёт.

Для чата использован запрос «Привет» с той же инструкцией о стиле, которую добавляет `ModelContextBuilder` в обычном приложении. Вместе с системным сообщением получилось 57 входных токенов. При 29 слоях на GPU ответы Q8_0 и Q4_K_M завершились штатно через 25 и 55 токенов. На CPU те же модели выдали 64 и 61 токен. Штатный парсер извлёк текст во всех четырёх случаях. Формулировки CPU и GPU различались. Первичная техническая проверка с укороченной подсказкой показала иное поведение, поэтому в отчёте о чате использованы результаты со штатной подсказкой. [Подготовка сообщений](../app/src/main/java/com/example/aiassistent1/domain/context/ModelContextBuilder.kt) · [Парсер ответов](../app/src/main/java/com/example/aiassistent1/domain/parser/AssistantResponseParser.kt)

## Замеры

Вход календаря содержал 285 токенов. Q8_0 выдала 30 токенов, Q4_K_M — 31. Все четыре сочетания дошли до токена конца ответа. Контекст — 2048, batch и microbatch — 64, потоков CPU — 4, сэмплер — greedy. В прогретом проходе модель и скомпилированные ядра оставались в памяти. Перед повтором очищался KV-кеш, создавался новый сэмплер и отключалось наблюдение за событиями очереди. Скорость генерации рассчитана как число выходных токенов, делённое на время декодирования.

В таблице приведены результаты двух отдельных запусков для каждого сочетания модели и вычислителя. В каждом запуске был один прогретый повтор.

| Модель и режим | Инициализация, с | Обработка прогретого запроса, с | Прогретая генерация, токенов/с |
| --- | ---: | ---: | ---: |
| Q8_0 · CPU | 0,65–0,68 | 7,17–7,23 | 9,62–13,86 |
| Q8_0 · OpenCL, 29 слоёв | 38,75–39,38 | 9,00–9,04 | 3,24–3,25 |
| Q4_K_M · CPU | 0,64–1,60 | 8,16 | 9,95 |
| Q4_K_M · OpenCL, 29 слоёв | 43,13–43,40 | 10,14–10,26 | 4,24–4,25 |

Время инициализации включает подготовку вычислителя, весов и контекста. Для OpenCL в новом процессе драйвер также компилировал ядра. Эти измерения относятся к одному телефону, одной прошивке и короткой календарной команде. Температура и частоты процессоров не фиксировались. Результат для других моделей, размеров контекста и Android GPU требует отдельных измерений.

## Изменения в сборке

Флаг Gradle `assistantOpenClProbe=true` добавляет в debug-вариант диагностический сервис и необязательное объявление драйвера. Нативный плагин собирается для `arm64-v8a`. Заголовки и библиотека для линковки Khronos закреплены версией и SHA-256. В APK входит один комплект библиотек Llamatik 1.10.1. Только `libggml-opencl.so` имеет ELF-зависимость от системной `libOpenCL.so`. Библиотека производителя берётся из Android. В диагностический APK включены тексты MIT, Apache-2.0 и атрибуция YaRN. [Конфигурация сборки](../app/src/main/cpp/gpu/opencl/CMakeLists.txt) · [Ведомость компонентов](../app/src/main/assets/licenses/OpenCL-NOTICE.txt)

Две детали потребовались для запуска на этом драйвере.

1. Закреплённая ревизия GGML ссылается на `clCreateBufferWithProperties` в резервной ветке для больших буферов Qualcomm. Обязательный импорт мешал загрузить плагин на драйвере OpenCL 2.0 ещё до открытия модели. Адаптер разрешает символ при обращении к этой ветке и возвращает ошибку, если драйвер не поддерживает запрошенные свойства. [Адаптер](../app/src/main/cpp/gpu/opencl/optional_buffer.cpp) · [Спецификация Khronos](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/clCreateBufferWithProperties.html)
2. Движок сверяется с глобальным реестром GGML даже при явно переданном устройстве. В первой версии диагностический счётчик выводил ноль и проверка прерывалась. Диагностика теперь регистрирует плагин, выбирает устройство именно из реестра OpenCL и освобождает собственную регистрацию после освобождения контекста и модели. [Загрузка и генерация](../app/src/openclProbe/cpp/model.cpp) · [Проверка событий GPU](../app/src/openclProbe/cpp/trace.cpp)

В контрольной сборке отключили объявление `uses-native-library`. На этом Redmi процесс приложения получил `dlopen failed: library "libOpenCL.so" not found`. Обе модели при явном запуске CPU вернули календарный JSON с названием «Встреча». После проверки на телефон вернули диагностическую сборку с доступом к драйверу, сверили SHA-256 установленного APK и запустили главный экран. Правила видимости библиотек определяют версия Android и целевой API приложения. [Документация Android](https://developer.android.com/guide/topics/manifest/uses-native-library-element)

Собраны обычный и диагностический debug APK для arm64. Обычный содержит 20 нативных библиотек, диагностический — 22. У обеих сборок проверено выравнивание ELF и ZIP на 16 КиБ. Физическое устройство использует страницы 4 КиБ. В объединённом release-манифесте отсутствуют диагностический сервис и объявление OpenCL. Из 853 модульных тестов приложения 852 прошли, один отчётный тест пропущен по его условию `CALENDAR_PROMPT_EVALUATION`. Он требует отдельной завершённой сравнительной оценки календарных подсказок.

## Повторить на устройстве

Сборка выполнялась в Windows с Android NDK 28.2.13676358, CMake 3.22.1 и Python 3 на компьютере. При одном подключённом Android-устройстве и нужном GGUF в каталоге приложения `Android/data/com.example.aiassistent1/files/models` команды ниже собирают и устанавливают оба APK. Их выполняют из корня проекта в PowerShell.

```powershell
.\gradlew.bat :app:assembleDebug :app:assembleDebugAndroidTest '-PassistantOpenClProbe=true' '-Pandroid.injected.build.abi=arm64-v8a'
adb install -r -t app/build/intermediates/apk/debug/app-debug.apk
adb install -r -t app/build/intermediates/apk/androidTest/debug/app-debug-androidTest.apk
```

Проверить драйвер, затем полную выгрузку Q8_0 и получить JSON из кеша приложения.

```powershell
$probeClass = 'com.example.aiassistent1.data.engine.OpenClProbeInstrumentedTest'
$runner = 'com.example.aiassistent1.test/androidx.test.runner.AndroidJUnitRunner'
$modelFile = 'calendar-assistant-v12.67-Qwen3-0.6B-Q8_0.gguf'
adb shell am instrument -w -e class $probeClass -e openclProbe driver -e run driver-check $runner
adb shell am instrument -w -e class $probeClass -e openclProbe opencl -e gpuModel $modelFile -e gpuLayers 29 -e scenario calendar -e warmCompare true -e run calendar-q8 $runner
adb exec-out run-as com.example.aiassistent1 cat cache/opencl-probe-calendar-q8.json
```

Для CPU задать `-e openclProbe cpu -e gpuLayers 0`, для частичной выгрузки — `-e openclProbe opencl -e gpuLayers 1`, для чата — `-e scenario chat`. Для Q4_K_M выбрать второе имя файла. Каждый запуск получает своё значение `-e run`. Контрольный APK собирается с дополнительным свойством `'-PassistantOpenClProbeHideDriver=true'`. На испытанном Redmi с Android 13 проверка драйвера с `-e expectHidden true` ожидает отказ, а запуск CPU должен вернуть ответ.
