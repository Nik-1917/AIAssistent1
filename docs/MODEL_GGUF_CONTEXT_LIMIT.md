# Автоматический предел контекста из GGUF

Дата: 2026-10-02.

## Что изменилось

При импорте и выборе установленной модели приложение читает `general.architecture` и соответствующий `[архитектура].context_length` из GGUF. Именно этот параметр llama.cpp читает в `n_ctx_train`. Например, для архитектуры `qwen3` используется `qwen3.context_length`, а значение другой архитектуры или `rope.scaling.original_context_length` не подменяет его.

В обеих вкладках настроек модели показан текст «Предел контекста модели: N токенов». Максимум шкалы определяется отдельно для выбранного файла. Текущий допустимый размер сохраняется; превышение уменьшается. Контекст и место под ответ сохраняют соотношение 2:1. Метки значений по умолчанию также ограничиваются доступным диапазоном. Выбор вкладки настроек не меняет режим разговора.

Потолок шкалы округляется вниз до шага 512: например, при значении 3000 доступны максимум 2560 токенов контекста и 1280 токенов ответа. При пределе ниже 512 остаётся одна чётная позиция и обе шкалы выключены. При больших окнах сохраняется округление, но ограничивается число декоративных делений Compose.

Если параметр отсутствует, не поддерживается или файл не удаётся прочитать, показывается «Предел контекста модели не определён. Потолок приложения: 8192 токенов.». Это резервное ограничение приложения, а не подтверждённая характеристика файла.

## Как применяется ограничение

- При чтении профиля метаданные определяются до нормализации сохранённых параметров. Уже установленные файлы получают предел при следующем выборе или запуске приложения.
- При сохранении значение из callback интерфейса не считается источником предела: читаются метаданные целевой модели, затем связанная пара записывается одной транзакцией DataStore.
- Перед загрузкой native-контекста движок самостоятельно проверяет файл. Защита действует также для временного окна сводки конференции. Меньший специальный лимит ответа сохраняется.
- Настройки во время генерации применяются после текущего запроса, как и прежде. При смене модели сбрасывается предел загруженного движка.
- Если импорт восстанавливает отсутствовавший файл с уже выбранным именем, подписка на параметры запускается заново.

## Чтение файла

`GgufMetadataReader` поддерживает GGUF v2/v3, оба порядка байтов, `UINT32`/`UINT64` для длины контекста в диапазоне 2..Int.MAX_VALUE и произвольный порядок двух нужных ключей. Допустимы дефисы и подчёркивания в именах архитектур, например `command-r` и `nemotron_h`. Чтение выполняется вне главного потока. После обнаружения обоих ключей оно прекращается; веса не загружаются, массивы токенизатора пропускаются без создания массивов в памяти.

Размеры, счётчики и смещения проверяются относительно файла. Есть пределы работы: 256 МиБ области метаданных, 100 000 записей, 2 000 000 пропускаемых строк массива. Неподдерживаемые и повреждённые метаданные дают неизвестный предел. Это не проверка целостности всей модели.

Кеш содержит до 16 файлов, привязан к каноническому пути, размеру и времени изменения. После обычной замены файла метаданные читаются заново. Изменение содержимого с сохранением всех трёх признаков не обнаруживается этим кешем. Метаданные не сохраняются в DataStore.

## Почему так лучше

Произвольный общий предел 8192 заменён характеристикой выбранного файла. Небольшая модель ограничивает настройки, большая допускает выбор большего окна, а текущий размер автоматически не увеличивается. Одинаковое правило в интерфейсе, сохранении и движке исключает обход ограничения старой настройкой или временным профилем. Предел GGUF описывает модель; наличие памяти для выбранного окна на конкретном телефоне проверяется при реальной загрузке.

## Проверки

Добавлены JVM-тесты бинарного чтения, обрезанных файлов и некорректных длин, смены файла, ограничений обеих шкал, больших окон без переполнения, ожидания записи интерфейса, независимости профилей, восстановления настроек из файла DataStore и параметров native-загрузки через тестовый runtime. Последний проверяет интеграцию Kotlin, а не GGUF-инференс на устройстве.

Итог проверки 2026-10-02: все 444 JVM-теста прошли, включая 21 новый; ошибок и пропусков нет. `:app:assembleDebug` выполнен успешно. `:app:lintDebug` завершён без ошибок: 42 предупреждения и 2 подсказки. `git diff --check` прошёл. Проверка интерфейса и инференса на физическом телефоне не выполнялась.
