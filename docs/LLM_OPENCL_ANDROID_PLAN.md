# Второй способ генерации на GPU в Android-приложении

Проверка на 18 ноября 2026 года. Проект `AIAssistent1`, снимок кода `6f1caf6`. Статус — исследование и план. Первый предлагаемый результат разработки — ответ нашей GGUF-модели с подтверждёнными вычислениями OpenCL в тестовой сборке.

19 ноября 2026 года этапы 1–2 проверены на физическом Redmi Note 11E Pro. Q8_0 и Q4_K_M выполнили обработку запроса и генерацию через OpenCL с 1 и с 29 слоями на Adreno 619. Результаты, измерения CPU/GPU и команды воспроизведения приведены в [отчёте об испытаниях](LLM_OPENCL_ANDROID_PROBE.md). Оценки ниже описывают сведения, доступные при составлении плана 18 ноября.

20 ноября 2026 года OpenCL включён в обычные debug и release. Порядок «Авто» — Vulkan → OpenCL → CPU. Работа обеих GGUF-моделей и переход на CPU проверены на Redmi. [Реализация и испытания](LLM_OPENCL_AUTOMATIC_ANDROID.md)

## План внедрения

### 1. Проверить доступ к драйверу из нашего приложения

Начать с диагностической сборки `arm64-v8a` на Redmi. В манифесте внутри `application` объявить `<uses-native-library android:name="libOpenCL.so" android:required="false" />`. У проекта `minSdk 30`, `targetSdk 36`. На Android 12+ при таком target Android требует явного объявления необязательной библиотеки производителя. Производитель также должен открыть её обычным приложениям. Выполнять тест в существующем непубличном процессе `:llm`, под UID приложения, с тем же манифестом и ABI, что у продукта. [AndroidManifest](../app/src/main/AndroidManifest.xml) · [Android Developers](https://developer.android.com/guide/topics/manifest/uses-native-library-element) · [Правила доступности библиотек](https://source.android.com/docs/core/permissions/namespaces_libraries)

Проба вызывает `dlopen("libOpenCL.so")` и проверяет необходимые функции. Записать найденный GPU, производителя, версию драйвера, версию платформы и OpenCL C, доступность компилятора, FP16, подгруппы для 3.x, лимит отдельного выделения и возможности изображений. На GPU собрать и выполнить маленькое ядро с известным ответом, прочитать результат. При отказе сохранить этап и краткий журнал компиляции без содержимого пользовательских запросов. Сначала проверить итоговый манифест, ABI и видимость библиотеки. Ошибку своей сборки исправить и повторить тест. При воспроизводимом отказе конкретной прошивки зафиксировать причину и оставить CPU для Redmi. Плагин можно независимо испытать на Adreno 750/830.

### 2. Проверить нашу GGUF-модель в тестовой сборке

Собрать отдельный `libggml-opencl.so` из того же GGML, что и AAR. Использовать существующий общий `libggml-base.so` и один реестр устройств. Добавить настройки и зависимости OpenCL в отдельную область CMake, включить встроенные ядра и оптимизации Adreno. Для линковки использовать изолированный каталог сборки Khronos. Системный NDK разработчика для этого менять не требуется. На Windows проверить поиск host Python для встраивания файлов `.cl`. [Существующая сборка плагина](../app/src/main/cpp/gpu/CMakeLists.txt) · [CMake OpenCL](https://github.com/ggml-org/llama.cpp/blob/961e9a3e46ca4cf7e6e86cfceb5b5e32084bf5f0/ggml/src/ggml-opencl/CMakeLists.txt)

Проверить через `llvm-readelf`, что только опциональный плагин зависит от системной `libOpenCL.so` с точным Android-именем. В APK проверить отсутствие частной копии `libOpenCL.so` и второго CPU/GGML. Запустить тест в процессе приложения без библиотеки или на устройстве, где она закрыта, и получить полноценный CPU-ответ.

Тест напрямую выбирает устройство из реестра OpenCL. Сначала запускает один слой Q8_0, затем пробует рабочее число слоёв по бюджету памяти. Выполнить обработку запроса и генерацию нескольких десятков токенов. В диагностическом режиме записать для обеих фаз успешно завершённые OpenCL-команды вычисления модели, включая умножение матриц, на очереди выбранного GPU, число выгруженных слоёв и полный ответ. Сравнить с CPU на тех же входных данных. Для календаря проверить готовый JSON и ожидаемое действие на тестовом примере. Повторить отдельно для Q4_K_M. При сбое взять первое сообщение компилятора или проблемную операцию. Решение о поддержке каждой связки «устройство + драйвер + модель» принимать по её результату.

### 3. Встроить выбор вычислителя и обработку ошибок

- Провести идентификатор `CPU / VULKAN / OPENCL` через параметры нативной попытки, Binder, JNI и результат. В JNI выбирать устройство через реестр конкретного плагина. Сейчас нативный код ищет первый GPU глобально, а Kotlin восстанавливает название «Vulkan» из количества слоёв. При двух плагинах оба места должны получать идентичность реально выбранного устройства. [JNI](../app/src/main/cpp/automatic_llama_jni.cpp) · [Рабочий процесс](../app/src/main/java/com/example/aiassistent1/data/engine/LlamaWorkerService.kt) · [Модель результата](../app/src/main/java/com/example/aiassistent1/domain/model/InferenceExecution.kt)
- В режиме «Авто» предложен порядок **Vulkan → OpenCL → CPU**. Первый пригодный GPU проходит проверку модели. При устойчивом отказе Vulkan до вывода первого фрагмента ответа попробовать OpenCL. Сбой драйвера, зависание или аварийное завершение требуют нового рабочего процесса перед следующей попыткой. При нехватке общей RAM заново оценить доступную память, чтобы не повторять заведомо неподходящее выделение. В режиме «CPU» сразу выполнять запрос без открытия GPU-библиотек. [Выбор режима и повтор](../app/src/main/java/com/example/aiassistent1/data/engine/LlamatikEngine.kt)
- После начала вывода ответа при сбое GPU использовать один уже предусмотренный повтор на CPU. Один `GenerationEvent.Restart` заменяет частичный ответ в той же записи. Отмена прекращает все попытки. Сохраняются однократная готовность, озвучивание и однократное выполнение календарной команды. Продолжать применять сериализацию запросов разных владельцев. Покрыть также отмену между попытками и падение процесса. [Архитектура текущей реализации](LLM_AUTOMATIC_GPU_CPU.md)
- Разделить результаты проверки, причины отказа, ключи совместимости и повторное использование загруженной модели по API, драйверу, устройству, версии плагина/приложения и экземпляру GGUF. Добавить вычислитель в нативный ключ проверки модели. Отказ Vulkan не должен исключить OpenCL. Ошибки формата или компиляции связывать с подтверждённой причиной. Отмену и временную нехватку памяти не записывать как постоянную несовместимость. [RemoteLlamaRuntime](../app/src/main/java/com/example/aiassistent1/data/engine/RemoteLlamaRuntime.kt)
- Сохранить ограничения существующего менеджера памяти. В этой версии GGML значение свободной памяти OpenCL вычислено из общего объёма с вычетом 1 GiB. Это верхняя оценка. При объёме до 1 GiB включительно GGML возвращает ноль, а текущая проверка `device.freeBytes <= 0` пропускает ограничение. Ввести отдельное представление для неизвестной оценки и нулевого бюджета. Учитывать доступную RAM Android, резерв, размеры тензоров и промежуточных буферов, максимальный размер одного выделения `CL_DEVICE_MAX_MEM_ALLOC_SIZE`. На общей памяти телефона RAM и «память GPU» перекрываются. [Расчёт в GGML](https://github.com/ggml-org/llama.cpp/blob/961e9a3e46ca4cf7e6e86cfceb5b5e32084bf5f0/ggml/src/ggml-opencl/ggml-opencl.cpp#L8079-L8089) · [Проверка бюджета в приложении](../app/src/main/java/com/example/aiassistent1/data/engine/LlamatikEngine.kt)

### 4. Показать результат в «Настройки → Вычисления AI»

Сохранить выбор «Авто» и «CPU» по имени модели и по двум существующим профилям. В разделе «Последний запуск» показывать фактически использованный вариант, например «GPU · OpenCL», «GPU + CPU · OpenCL» или «CPU», а также устройство, количество слоёв, причину выбора, время до первого токена и скорость. Если Vulkan пропущен и OpenCL успешно сработал, итоговый статус должен называть OpenCL. Длинный журнал компилятора остаётся в диагностике тестовой сборки. ### 5. Проверить выпуск и принять решение

| Испытание | Критерий |

| Автотесты автоматики и настроек | Проверить выбор Vulkan при двух доступных API, переход на OpenCL при отказе Vulkan, переход на CPU при отказе обоих, обход обеих проб в ручном CPU, обнуление частичного ответа и смену ключа кеша после обновления драйвера. На контрольном телефоне выбрать OpenCL из теста, даже если «Авто» предпочитает Vulkan. При отказе на Redmi проверить тот же запрос на CPU. |

Для календаря сверить параметры, число созданных событий в изолированном наборе данных. Для чата и выжимки — целостность потока. |
| Время и память | Сравнить CPU и OpenCL на одной модели, с одинаковыми запросом, контекстом, batch, параметрами генерации и числом токенов. Пример серии — три холодных запуска и пять прогретых. Раздельно показать подготовку, время до первого токена, обработку запроса, генерацию, пиковый PSS и тепловое состояние. Вычислительный профиль для доказательства исполнения отключить в замерах скорости. |

Проверить зависимости ELF, атрибуции, выравнивание ELF и APK на 16 KiB для 64-битных библиотек, установку из выпускной сборки и тест на устройстве/эмуляторе с 16 KiB. Первый этап, предлагаемый к подтверждению, — **диагностическая сборка и испытание Q8_0 на реальном устройстве** (пункты 1–2). Если модель генерирует текст с подтверждённым исполнением на GPU, можно переходить к автоматическому выбору и интерфейсу. Если отказ воспроизводится только на Redmi, для него фиксируется точная причина и рабочий CPU. Поддержку остальных устройств можно оценить по их собственным испытаниям.
