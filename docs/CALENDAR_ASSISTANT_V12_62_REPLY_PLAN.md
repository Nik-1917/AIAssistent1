# План V12.62: произношение времени только в reply

Статус на 29 сентября 2026 года: пользователь подтвердил выполнение
словами «запускаем обучение». Набор V12.62 подготовлен, обучение и сборка
завершены, файл доставлен на телефон с проверкой SHA-256. Проверка генерации
завершена: 66 из 98 случаев прошли, полное исправление произношения не
подтверждено. Результаты и все найденные ошибки зафиксированы в
[отчёте V12.62](CALENDAR_ASSISTANT_V12_62_TRAINING_RESULTS.md).

Пользователь уточнил: «надо ещё в правилах объяснить правила ответа в репли».
Это разрешённое исключение из прежнего запрета на изменение файлов правил,
ограниченное произношением времени в reply. Добавлен отдельный документ
[правил V12.62](CALENDAR_ASSISTANT_V12_62_REPLY_CLOCK.md) и раздел со ссылкой
на него в [основной спецификации](CALENDAR_ASSISTANT_TRAINING_SPEC.md).
Другие разделы основной спецификации и исторические документы сохранены.

## Запрос и проверенные факты

Пользователь сообщил, что на запрос «двенадцать часов пятнадцать минут
завтра едем» модель отвечает «едем в половине первого». Требуемый ответ:
«Едем завтра в четверть первого». Для известного времени 12:15 форма
«в половине первого» неверна: она означает 12:30.

В train V12.61 строка 2166, case_id V1253T1215, уже содержит правильную пару:

- user: «В двенадцать пятнадцать завтра поставь сверку меню на четверть часа.»
- reply: «Сверка меню завтра, в четверть первого, на четверть часа.»
- params.starts_at: 2027-09-01T12:15; params.duration_min: 15.

Пользователь уточнил охват: каждое значение минуты каждого часа, включая
01–29 и все формы «без ...» с 31-й до 59-й минуты. Полный охват —
24 часа × 60 минут = 1440 сочетаний, а не только минуты, кратные пяти.

После расширения проверки на все минуты найдены 481 обучающая и
163 валидационные записи calendar_add, в которых время известно, а reply
содержит только название события. Всего записей calendar_add с явным
временем HH:MM: 2664 в train и 397 в validation. Все найденные ответы
только с названием имеют историческую метку v12.1.
В действующем контракте релиза v12.57 допускается произношение известного
времени в reply; существующий проверяющий код это уже поддерживает.

Эти наблюдения не доказывают причину конкретной ошибки модели. Полный JSON
сообщённого пользователем ответа не получен; правильность params в этом
ответе отдельно не подтверждена. Сравнение только потерь обучения недостаточно
для проверки исправления.

## Требуемые формы

| Известное время | Фрагмент reply |
| --- | --- |
| 12:00 | в двенадцать часов |
| 12:01 | в одну минуту первого |
| 12:02 | в две минуты первого |
| 12:14 | в четырнадцать минут первого |
| 12:15 | в четверть первого |
| 12:16 | в шестнадцать минут первого |
| 12:21 | в двадцать одну минуту первого |
| 12:29 | в двадцать девять минут первого |
| 12:30 | в половине первого |
| 12:31 | без двадцати девяти минут час |
| 12:32 | без двадцати восьми минут час |
| 12:35 | без двадцати пяти минут час |
| 12:38 | без двадцати двух минут час |
| 12:39 | без двадцати одной минуты час |
| 12:40 | без двадцати минут час |
| 12:45 | без четверти час |
| 12:50 | без десяти час |
| 12:55 | без пяти минут час |
| 12:58 | без двух минут час |
| 12:59 | без одной минуты час |

Таблица иллюстрирует формы; будущая проверка должна охватить каждую минуту,
включая не показанные здесь значения:

- 00: точный час;
- 01–29: прошедшие минуты следующего по названию часа, с правильными
  окончаниями «минуту / минуты / минут»; для 15 — «в четверть ...»;
- 30: «в половине ...»;
- 31–59: оставшиеся до следующего часа минуты, от «без двадцати девяти минут»
  до «без одной минуты»; для 45 — «без четверти ...»;
- для 50 сохранена ранее указанная пользователем краткая форма
  «без десяти ...», обозначающая те же десять оставшихся минут.

Для остальных часов используются соответствующие названия следующего часа:
например, 13:15 — «в четверть второго», 13:30 — «в половине второго»,
13:35 — «без двадцати пяти минут два», 23:45 — «без четверти двенадцать».
«В половине» — форма для времени события. Длительность «на тридцать минут»
сохраняется как длительность и не превращается во время на часах.

## Подтверждённые изменения

1. Создать отдельный набор V12.62 на основе V12.61. Сохранить состав и порядок
   записей, входные system/user и все поля целевого JSON, кроме reply.
   Применить описанное дополнение правил reply. Остальные правила, Android-код,
   обработка JSON, настройки генерации и прежние релизы остаются исходными.
   Версия набора — V12.62; схема ответа остаётся v12.57.
2. Вручную привести фразы времени в reply для всех минут 00–59 и всех
   часов 00–23 к указанным формам, сохраняя уже подходящие ответы.
   В старых ответах только с названием дополнить reply известным временем.
   Не добавлять отсутствующее время. Сохранить названия, даты, значения,
   длительности, смысл команд и все структурированные параметры.
3. Проверить и начало, и окончание интервалов, если они присутствуют в reply.
   Названия событий, цитаты и длительности не обрабатывать как часы.
   Проверить произношение каждого из 1440 сочетаний, без пропусков между
   соседними минутами. Существующее покрытие суток должно остаться полным.
4. Подготовить отдельный буквальный реестр исправлений с исходным и новым reply,
   указанием строки и основанием времени. Сборщик только применяет рассмотренные
   исправления; языковые фразы не создаются программным шаблоном.
   Проверку новых ответов проводить по действующему контракту v12.57, сохраняя
   происхождение старых строк отдельно от версии проверяемого ответа.
   В новом реестре целостности явно учесть разрешённое дополнение основной
   спецификации; исторические контрольные суммы V12.61 не переписывать.
5. Проверить, что после исключения поля reply целевые JSON совпадают с V12.61,
   а входные сообщения не изменились. Проверить все 1440 сочетаний, отсутствие
   путаницы между :15 и :30, переходы :29 → :30 → :31 и :59 → следующий час,
   полночь и полдень, длительности и интервалы. Проверить род, падеж и окончания
   числительных. Повторить проверку лимита токенов и целевой маски.
6. После успешной подготовки обучить V12.62 с прежними параметрами, собрать
   Q4_K_M. На готовом GGUF проверить пользовательский запрос и независимые
   примеры требуемых форм; оценить соответствие reply времени и отдельно
   сохранность intent/params. Изменение только reply в данных не гарантирует
   неизменность всех выходов переобученной модели, поэтому обе части нужны.
7. Зафиксировать фактические результаты в итоговом Markdown-отчёте, перенести
   файл calendar-assistant-v12.62-Q4_K_M.gguf в Downloads телефона и проверить
   SHA-256. Если проверка ответов выявит ошибки, отразить их явно и не объявлять
   проблему решённой по факту завершения обучения.

Документы правил не поступают в модель автоматически: существующий тренер
обрабатывает messages из JSONL. Правила должны отражаться в эталонных reply
и проверках набора. Системный промпт этим дополнением не изменяется.

## Подготовка набора

Сохранены 4096 обучающих, 670 валидационных и 361 дополнительных проверочных
запись (5127 всего). Изменены 749 reply: 700 ответов только с названием
дополнены известным временем; ещё 49 приведены к согласованным формам
«в половине» и «без десяти». Полная сетка 1440 значений проверена.

476 полных фраз для повторяющихся пар «название + время» и 49 стилевых
правок записаны буквально в `docs/calendar_v12_62_manual/`. Сборщик переносит
эти строки, не сочиняя ответы. Состав, порядок и все входные сообщения
совпадают с V12.61. После исключения reply целевые JSON также совпадают.

У 700 исходных строк историческая метка `contract_version: v12.1` заменена
на действующую `v12.57`: старый проверяющий контракт требовал ответ только
с названием и отвергал добавленное время. Это служебная метка строки,
она не входит в сообщения модели. Исходные метки сохранены в
`correction_log.json`; код существующих контрактов не изменялся.
